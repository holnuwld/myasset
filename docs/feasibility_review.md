## 2. 시트 스키마(`sheet_schema.md`) vs 기술 명세(`technical_spec.md`) 정합성 검증

### 2.1 [결함 1: High] `currency`(통화) 컬럼 부재 및 판별 메커니즘 불일치
- **현상**: `Asset` 모델에는 `currency: Currency`가 정의되어 있으나 `sheet_schema.md`의 `자산원장` 13개 컬럼(A~M)에는 통화 컬럼이 누락되어 있음.
- **리스크**: 구글 시트에서 데이터를 읽어올 때 모든 자산이 `KRW`로 파싱되어, 미국 주식(예: `AAPL`, `TSLA`)이나 외화 예금의 매수단가 및 현재가가 원화로 오인되거나 환율 연산이 누락될 위험.
- **권고 대응**: `sheet_schema.md` N열에 `통화`(`currency`, 기본값 `KRW`, 외화 시 `USD`)를 추가하거나, `sub_type` 및 티커(영문 티커이면서 `.KS`/`.KQ`가 아닌 경우) 기반 자동 추론 헬퍼 구현.

### 2.2 [결함 2: Medium] `Allocation` 및 `Alerts` 탭의 구체적 컬럼 스키마 누락
- **현상**: `Allocation`(자산배분) 및 `Alerts`(알림센터) 탭의 정확한 헤더명과 열 순서가 명시되지 않음.
- **권고 대응**:
  - `Allocation` 탭: `[카테고리, 평가금액(KRW), 현재비중(%), 목표비중(%), 편차(%p), 리밸런싱여부]`
  - `Alerts` 탭: `[발생일시, 알림ID, 심각도, 알림유형, 자산ID, 자산명, 금융기관, 알림메시지, 권고행동, 기회비용(원)]`

## 3. 구글 시트 연동 및 데이터 I/O 리스크 분석

### 3.1 [결함 3: High] `batch_update` 시 문자열 변환에 따른 시트 수식/숫자 인식 오류
- **현상**: `values: [[str(a.current_price), str(a.valuation_krw)]]` 형태로 전송 시 `RAW` 모드로 처리되어 구글 시트에 텍스트로 저장됨. 시트 내 `=SUM()` 수식 파괴 및 좌측 정렬 문제 발생.
- **권고 대응**: `batch_update` 시 반드시 `value_input_option='USER_ENTERED'` 옵션을 지정하고 수치형 데이터 보존. 기존 `=GOOGLEFINANCE` 수식이 있는 행은 건너뛰는 분기 처리 필요.

### 3.2 [결함 4: High] `append_alerts` 반복 실행 시 알림 무한 중복 누적
- **현상**: 스케줄러나 CLI 다회 실행 시 매번 동일한 만기/유휴 알림이 누적되어 `Alerts` 탭이 수백 개의 중복 행으로 오염됨.
- **권고 대응**: 당일 최신 활성 알림 세트로 전체 갱신(Clear & Overwrite)하는 스냅샷 교체 방식 또는 `[발생일자 + asset_id + alert_type]` 복합 키 기반 중복 삽입 방지 로직 적용.

### 3.3 [결함 5: Medium] 시트 입력 데이터의 유연한 파싱(Sanitization)
- **현상**: 시트에 `1,000,000`(쉼표 포함), `3.5%`(퍼센트 기호), 빈칸(`""`) 유입 시 Python `Decimal` 변환 중 `InvalidOperation` 크래시 발생.
- **권고 대응**: 쉼표/기호 제거 및 빈칸 기본값 치환 밸리데이터 구현.

## 4. 도메인 비즈니스 로직 및 엣지 케이스 검증

### 4.1 만기 자산 알림 (`Maturity Alert`) 엣지 케이스
- **해지 완료 자산**: 이미 해지/수령했으나 시트에 남아있는 경우 `notes`에 `[해지완료]` 포함 시 알림 대상에서 제외.
- **다중 날짜 포맷**: `YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY/MM/DD`를 포괄하는 파서 적용.

### 4.2 유휴 자금 알림 (`Idle Cash Alert`) 엣지 케이스
- **마이너스 통장**: 음수 잔액 계좌(`valuation_krw < 0`)는 유휴자금 판정에서 원천 제외.
- **외화 계좌**: 달러 계좌 방치 시 원화 파킹통장(3.0%) 대신 외화 RP/발행어음 기준 문구 분기.

### 4.3 자산 배분 비중 100% 보정 로직 정합성
- **ZeroDivisionError 방어**: 총자산 0원 시 모든 비중 0.00% 반환.
- **반올림 오차 흡수**: 최대 비중 카테고리에서 잔여 편차($\pm 0.01\%$) 흡수 알고리즘 검증 완료.

## 6. GitHub Pages 모바일 웹 배포 및 보안/CORS 검증

### 6.1 보안 리스크: 정적 웹 환경에서의 자격증명(Credentials) 노출 원천 차단
- **위험 요소**: GitHub Pages는 순수 정적 호스팅이므로, Google Cloud 서비스 계정 키(`credentials.json`)나 마스터 API 키를 프론트엔드 코드에 포함하면 소스보기나 네트워크 탭을 통해 즉시 유출됨.
- **해결 방안: Google Apps Script (GAS) Web App 브릿지 아키텍처**:
  - 클라이언트가 Google Sheets API를 직접 호출하지 않고, 해당 스프레드시트에 바인딩된 **GAS를 웹 앱(Web App)으로 배포**하여 중간 브릿지 API로 사용.
  - GAS는 시트 내부 컨텍스트에서 실행되므로 외부 인증키 노출이 전혀 발생하지 않음.

### 6.2 CORS(Cross-Origin Resource Sharing) 이슈 해결
- GAS의 `ContentService.createTextOutput(JSON.stringify(response)).setMimeType(ContentService.MimeType.JSON)` 반환 방식은 Google 인프라에서 CORS를 자동 처리하므로 브라우저와의 비동기 통신(`fetch`)이 완벽 지원됨.

## 7. 비정형 거래 문자 파싱 엔진 및 무결성 검증

### 7.1 [결함 6: Critical] '변동금액(입출금)' vs '최종잔액' 구분 오류
- **해결 방안**:
  - `승인/출금/입금/결제` 키워드 인접 숫자는 `delta_amount`(변동금액)로 추출.
  - `잔액/잔여` 키워드 인접 숫자는 `final_balance`(최종잔액)로 추출.
  - 문자 내에 `final_balance`가 존재하면 원장의 잔액을 **최종 잔액으로 직접 일치(Direct Sync)**시켜 계산 누적 오차를 원천 방지.

### 7.2 [결함 7: High] 동명이인 / 유사 계좌 매칭 실패
- **해결 방안**:
  - `계좌번호 끝자리(4자리) 일치 > 금융기관명 일치 > 세부유형 일치` 3단계 스코어링 적용.
  - 매칭 신뢰도 80% 미만 또는 복수 계좌 동점 시 자동 커밋을 중단하고 사용자 수동 선택 드롭다운 호출.

### 7.3 [결함 8: High] 동일 문자 중복 붙여넣기 / 재전송 리스크
- **해결 방안**:
  - 문자 원문 정규화 후 **SHA-256 해시값**(`tx_hash`) 생성.
  - 최근 거래 해시 캐시와 대조하여 동일 해시 존재 시 `"⚠️ 이미 처리된 거래 내역입니다"` 경고와 함께 원장 갱신 원천 차단.

## 8. 오파싱 방지 Human-in-the-Loop '프리뷰 후 승인(Confirm)' 안전장치

- **모바일 웹**: 문자 입력 $\rightarrow$ 파싱 결과(유형, 금액, 잔액, 계좌 드롭다운) 모달 팝업 $\rightarrow$ 사용자가 `[최종 반영(Confirm)]` 클릭 시에만 시트 전송.

## 9. [v2.1 신규] GitHub Pages 공개 호스팅 시 제3자 열람 원천 차단 및 영지식 보안 체계

GitHub Pages는 오픈소스 리포지토리 또는 누구에게나 URL이 노출될 수 있는 정적 웹 호스팅 환경입니다. 제3자가 리포지토리나 웹사이트를 방문하더라도 개인 금융 데이터가 단 1바이트도 유출되지 않도록 하는 **영지식(Zero-Knowledge) 및 심층 방어(Defense-in-Depth) 체계**의 실현 가능성을 검증했습니다.

```
[제3자 / 공격자 접근]
         │
         ├─ 1. GitHub 소스 / 커밋 히스토리 / F12 개발자 도구 열람
         │     └─► [결과: 0바이트 무노출] 순수 UI 템플릿 코드만 존재, 개인 데이터 전무
         │
         ├─ 2. LocalStorage / SessionStorage 강제 추출
         │     └─► [결과: 암호문만 존재] AES-256-GCM 암호화 볼트 (Master Key 없으면 해독 불가)
         │
         ├─ 3. 무차별 대입 (Brute-force) 시도
         │     └─► [결과: 무력화] PBKDF2(100,000회)로 연산 부하 극대화 + 5회 실패 시 락아웃
         │
         └─ 4. GAS Web App 엔드포인트 무단 호출
               └─► [결과: 401 Unauthorized] 올바른 Bearer Token 부재 시 빈 응답 반환
```

### 9.1 개인 데이터 0바이트 무노출 검증 (Zero Data Exposure in Static Assets)
- **검증 항목**:
  - `web/index.html`, `web/app.js`, `web/style.css` 등 GitHub Pages에 배포되는 모든 정적 파일.
  - Git 커밋 히스토리, Releases, 브라우저 F12 개발자도구 (Sources, Elements, Network 탭).
- **검증 결과**:
  - 정적 에셋에는 오직 **UI 레이아웃 뼈대, 암호화 헬퍼 함수, DOM 이벤트 처리 로직**만 포함됩니다.
  - 사용자의 총자산, 개별 계좌명, 계좌번호, 주식 종목, 평가금액, 거래 내역 등 **어떠한 개인 금융 정보도 하드코딩되지 않으며, 빌드 산출물에도 일절 포함되지 않음을 확인(0바이트 무노출)**했습니다.
  - 제3자가 GitHub 리포지토리 전체를 클론하거나 F12로 사이트를 디버깅해도 볼 수 있는 것은 "비어있는 대시보드 템플릿과 로그인 잠금 화면"뿐입니다.

### 9.2 암호화 아키텍처 및 이중 방어선 (Defense-in-Depth) 타당성 검증
개인 금융 데이터는 오직 사용자가 입력한 마스터 비밀번호(또는 PIN)를 통해서만 복호화되어 브라우저 메모리에 일시 로드되는 **영지식 아키텍처**를 적용합니다.

1. **1차 방어선: Web Crypto API 기반 PBKDF2 + AES-256-GCM 암호화 볼트**:
   - **키 유도 (PBKDF2)**:
     - 알고리즘: `PBKDF2-HMAC-SHA256`, 반복 횟수(Iterations): **100,000회**, Salt: 계정 고유 난수(16바이트).
     - 효과: 사용자가 입력한 짧은 PIN(또는 패스프레이즈)으로부터 고강도의 256비트 대칭키(`CryptoKey`)를 유도. CPU/GPU 연산 비용을 강제하여 무차별 대입(Brute-force)을 수학적으로 무력화.
   - **데이터 암호화 (AES-256-GCM)**:
     - 브라우저 로컬 저장소(`localStorage`)에 저장되는 설정값(시트 연동 엔드포인트, 사용자 프로필, 임시 캐시 등)은 12바이트 IV(Initialization Vector)와 함께 **AES-256-GCM(Galois/Counter Mode)**으로 암호화되어 보관.
     - 인증 태그(Auth Tag)를 통한 무결성 검증이 내장되어 있어 임의 변조 시 복호화 실패.
2. **2차 방어선: GAS Web App Bearer 토큰 상호 인증**:
   - 구글 시트 원장 데이터를 가져오기 위해 클라이언트는 GAS Web App에 요청을 보냅니다.
   - 이때 요청 헤더 또는 페이로드에 암호화 볼트에서 복호화된 **`Bearer <Shared-Secret-Token>`**을 탑재.
   - GAS 백엔드는 `PropertiesService.getScriptProperties()`에 보관된 마스터 해시와 대조하여 일치할 때만 시트 데이터를 전송.
   - 엔드포인트 URL이 공개되더라도 제3자의 단순 호출은 즉시 `401 Unauthorized`로 거부되어 시트 데이터 열람이 원천 차단됩니다.

### 9.3 비활성 시간 메모리 자동 소거 (Auto-Lock) 및 브루트포스 방어
브라우저가 켜진 상태로 방치되거나 기기를 분실했을 때의 메모리 덤프 공격 및 무차별 대입 공격을 차단합니다.

1. **비활성 타이머 기반 메모리 자동 소거 (Inactivity Auto-Lock)**:
   - **동작 원리**: 사용자의 마우스 이동, 클릭, 터치, 키 입력을 감지하는 전역 이벤트 리스너 구동.
   - **자동 잠금**: 일정 시간(기본 **5분**, 설정 가능) 동안 사용자 인터랙션이 감지되지 않으면 즉시 발동.
   - **메모리 소거 (Wipeout)**:
     - JavaScript 런타임 메모리(전역 객체, State 변수)에 적재된 복호화된 자산 데이터, 복호화 키(`CryptoKey`), 베어러 토큰을 `null`로 덮어쓰고 Garbage Collection 유도.
     - UI를 즉시 `PIN/비밀번호 재입력 모달(Lock Screen)`로 전환하여 화면상의 금융 숫자 블러/은폐 처리.
2. **브루트포스(무차별 대입) 락아웃 방어**:
   - **클라이언트 락아웃**:
     - 5회 연속 잘못된 PIN 입력 시 **1분간 입력 비활성화(Exponential Backoff)**.
     - 10회 연속 실패 시 브라우저 내의 암호화 볼트(`localStorage`)를 영구 삭제(Self-Destruct/Wipe)하여 로컬 공격을 원천 무력화.
   - **서버(GAS) 레이트 리밋**:
     - `CacheService`를 활용하여 동일 IP 또는 클라이언트 식별자로부터 분당 10회 이상의 인증 실패 발생 시 일시적으로 요청을 드롭(HTTP 429).

### 12.1 항목별 정밀 검증 상세

#### 1. 보안 아키텍처 및 영지식 암호화 볼트 검증
- **PIN 잠금 화면 UI**:
  - `lockOverlay`를 통한 4자리 키패드 및 시각적 도트 피드백 정상 구현.
  - 초기 진입 시 대시보드와 FAB 바가 은폐(`display:none`)되어 데이터 노출 차단.
- **WebCrypto PBKDF2 키 유도**:
  - `iterations: 100000`, `hash: "SHA-256"` 적용으로 무차별 대입 연산 부하 강제 확인 (정상).
- **AES-256-GCM 암호화 볼트**:
  - 16바이트 난수 Salt, 12바이트 난수 IV를 `crypto.getRandomValues()`로 생성하여 안전한 대칭키 암복호화 구현.
  - `localStorage`에는 암호문(Ciphertext), Salt, IV만 보관되어 브라우저 저장소 직접 탈취 시에도 데이터 해독 불가 확인 (정상).
- **메모리 제로화(Zeroing)**:
  - `lockVault()` 실행 시 `activeAssets = []; currentParsedTx = null;`로 런타임 메모리 즉시 소거 확인 (정상).
- **[미흡 1] 5분 비활성 자동 잠금 (Inactivity Auto-Lock)**:
  - `lockVault()` 함수는 구현되어 있으나, 5분(300,000ms) 무입력 감지 시 `lockVault()`를 자동 호출하는 이벤트 리스너(`mousemove`, `keydown`, `touchstart`)가 누락됨.
- **[미흡 2] 브루트포스 락아웃 (Brute-force Lockout)**:
  - 잘못된 PIN 입력 시 실패 카운트 누적 및 5회 실패 시 1분간 입력 잠금 로직이 누락됨.

#### 2. 도메인 금융 연산 및 비즈니스 규칙 정밀도 검증
- **자산 배분 비중 100.00% 무오차 보정 (Invariant)**:
  - 7대 카테고리별 비중 반올림 후 잔여 오차(`diff = 100.00 - ratioSum`)를 최대 비중 카테고리(`maxCat`)에서 자동 흡수하도록 구현됨 (`ratios[maxCat] += diff`).
  - 총자산 0원 시 ZeroDivision 방어 및 합계 100.00% 불변식 완벽 유지 확인 (정상).
- **±5.0%p 리밸런싱 판정**:
  - `Math.abs(curr - target) >= 5.0` 조건 충족 시 `🚨 리밸런싱 권고 (+X.X%p)` 배지 표출 정상 작동 (정상).
- **만기 4단계 스마트 알림**:
  - `today` 기준일(2026-11-04) 대비 `diffDays < 0`(만기 경과 1건), `diffDays === 0`(만기 당일 1건), `diffDays <= 7`(만기 임박 1건), `diffDays <= 30`(만기 예정 1건) 4단계 라이프사이클이 정확히 분류되어 전용 가이드와 함께 렌더링됨 확인 (정상).
- **유휴자금 방치 경고 및 파킹통장(3.0%) 기회비용**:
  - `현금성`/`입출금` 자산 중 `이율 <= 0.5%` 및 `평가액 >= 1,000,000원` 조건 필터링 정상 작동.
  - `신한 주거래 수시입출금`(850만 원, 0.10%)에 대해 연간 추가 이자 기회비용 `₩ 246,500원` (`8,500,000 * (3.0% - 0.10%)`)이 정확히 계산되어 표시됨 확인 (정상).

- **거래문자 정규식 파서 (4종 샘플 및 범용 룰)**:

let inactivityTimer = null;
function resetInactivityTimer() {
  clearTimeout(inactivityTimer);
  // 대시보드가 열려있을 때만 타이머 가동 (5분 = 300,000ms)
  if (document.getElementById("mainDashboard").style.display !== "none") {

    }, 300000);
  }
}
['mousemove', 'keydown', 'touchstart', 'click'].forEach(evt => {
  window.addEventListener(evt, resetInactivityTimer);
});

// 권고 패치 2: 브루트포스 5회 실패 락아웃
let failedAttempts = 0;
let lockoutUntil = 0;

// verifyAndUnlock() 상단에 추가:
if (Date.now() < lockoutUntil) {
  const remainSec = Math.ceil((lockoutUntil - Date.now()) / 1000);
  showToast(`⛔ 5회 오류로 잠금 상태입니다. (${remainSec}초 후 재시도)`);
  clearPin();
  return;
}
if (currentPinInput !== DEMO_PIN) {
  failedAttempts++;
  if (failedAttempts >= 5) {

  } else {
    showToast(`⚠️ PIN 불일치 (${failedAttempts}/5회)`);
  }
  clearPin();
  return;
}
failedAttempts = 0; // 성공 시 카운트 초기화

### 17.2 4대 치명적 결함(Defect A, B, C, D) 상세 원인 규명

#### 1. [결함 A - CRITICAL] 실제 일봉 크롤링 부재 및 삼각함수(sin/cos) 가짜 곡선 조작
- **코드 위치**: `src/live_price_server.py` 라인 97~105
- **결함 내용**:
  ```python
  base_curve = 874000000 + (current_nav - 874000000) * (t_ratio ** 1.15)
  wave = math.sin(days_from_start * 0.12) * 8500000 + math.cos(days_from_start * 0.05) * 12000000
  nav = round(base_curve + wave)
  ```
- **원인 분석**:
  - 개발자가 네이버 및 야후의 과거 1년치 일봉 데이터를 실제로 크롤링하여 합산하지 않고, 시작점(8.74억)부터 끝점(현재 NAV)까지 $t^{1.15}$ 지수함수에 `math.sin`과 `math.cos` 노이즈를 섞어 **완전히 조작된 가짜 시계열**을 생성함.
  - 이로 인해 실제 시장의 급락, 반등, 횡보 이벤트가 전혀 반영되지 못하고 엉뚱한 수익률이 도출됨.

#### 2. [결함 B - CRITICAL] 오늘자 스냅샷 return_pct 분모 불일치로 인한 차트 마지막 날 수직 급등(+6.95%p) 결함
- **코드 위치**: `src/live_price_server.py` 라인 85~95 및 108~112
- **결함 내용**:
  - 과거 날짜 ($t < \text{today}$):  
    `ret_pct = round(((nav - ytd_base_nav) / ytd_base_nav) * 100, 2)`  
    $\rightarrow$ **분모가 연초 기준 자산(8.95억 원)**으로, 어제(2026-11-03) 수익률은 **+19.16%**로 계산됨.
  - 오늘 날짜 ($t = \text{today}$, `is_real_snapshot=True`):  
    `snap["return_pct"] = round(((current_nav - current_buy) / current_buy) * 100, 2)`  
    $\rightarrow$ **분모가 매입원금(8.31억/8.40억 원)**으로, 오늘(2026-11-04) 수익률은 **+26.11%** (실시간 시세 시 +28.63%)로 계산됨.
- **원인 분석**:
  - 하나의 차트 라인에 **'연초 대비 YTD 수익률'**과 **'매입원금 대비 누적수익률'**이라는 서로 다른 분모의 지표를 혼합하여, 마지막 날 하루 만에 수익률이 **+19.16% $\rightarrow$ +26.11%로 무려 +6.95%p 수직 폭등(수직 절벽)**하는 치명적 수식 오류가 발생함.
